# Triggers and rewrites

Two ways to attach mutation-time logic to a type, both declared as PyQL strings — never raw SQL.

## `Trigger`

```python
from pylon.schema import On, Timing, Trigger

@pylon.type
class Person:
    name: str
    Trigger(
        on=On.Insert,
        timing=Timing.After,
        handler="insert Log { note := __new__.name }",
    )
```

A real PostgreSQL trigger, declared as a class-body expression. `on` is an `On` bitmask (`On.Insert`, `On.Update`, `On.Delete` — combine with `|`, e.g. `On.Insert | On.Update`); `timing` is `Timing.Before`, `Timing.After`, or `Timing.InsteadOf`. `handler` is a PyQL statement, compiled to SQL at DDL-export time — it can perform its own mutations (`insert`/`update`/`delete`), same as any other PyQL statement. Trigger names are auto-generated by hashing at DDL-generation time; you never name one yourself.

### `__new__` / `__old__`

Reference the inserted/updated/deleted row via `__new__`/`__old__`, both backed directly by Postgres's own `NEW`/`OLD` trigger row variables:

```python
Trigger(on=On.Delete, timing=Timing.Before, handler="insert Log { note := __old__.name }")
```

Legality follows from which events are possible: `__old__` is legal only when `on` doesn't include `Insert` (an insert has no "old" row); `__new__` is legal only when `on` doesn't include `Delete` (a delete has no "new" row). A trigger combining `Insert` and `Delete` with no `Update` — an unusual but valid combination — can reference neither.

### Recursive triggers are rejected statically

A trigger whose own handler issues a mutation on the *same* type it's attached to, in a way that could re-fire itself, is rejected at `finalize()` time rather than left to blow Postgres's runtime recursion-depth limit at query time. The check walks the compiled handler for: a direct `insert`/`update`/`delete` on the owner type, the same wrapped in a `select (DML) { ... }`, and a `for x in ... union (...)` loop body containing one — matching the shapes real trigger handlers in Pylon's own test suite actually use. A DML nested inside a free tuple/set literal isn't walked and falls back to Postgres's own runtime guard, same as before this check existed.

### Trigger bodies compile eagerly

A trigger's handler is compiled — checked for syntax/resolution errors — at `finalize()` time, not only when the schema is finally exported to DDL. There's no declared return type to check (a trigger handler is a side-effecting statement, not a value producer), but a broken handler on a type nobody's exported yet no longer sits undetected. See [Validation](validation.md).

## `Rewrite`

```python
from pylon.schema import On, Rewrite

@pylon.type
class Person:
    name: pylon.Property[str,
        Rewrite(On.Insert, '.name ++ " (created)"'),
        Rewrite(On.Update, '.name ++ " (updated)"'),
    ]
```

A rewrite transforms a PyQL mutation's assigned value *before* it reaches the database — declared inside a `Property[T, ...]` annotation. `On.Insert` and `On.Update` each support at most one rewrite per property; a mutation not covered by a matching rewrite writes the value as given, untransformed.

> Rewrites are currently only compiled/enforced when declared on a `Property` — the `Rewrite` docstring also mentions `Link[T, ...]`, but nothing in the compiler reads a link's rewrites yet. Don't rely on a link-level `Rewrite` having any effect today.

Like a default or computed pointer, a rewrite handler is compiled at `finalize()` time and its produced type checked against the property's own declared type:

```python
name: pylon.Property[str, Rewrite(On.Insert, "1")]
# SchemaError: rewrite handler type mismatch for '...Person.name (rewrite)': expected text, handler produces __int_literal
```

See [Validation](validation.md) for the same best-effort scope every other type-consistency check shares.
